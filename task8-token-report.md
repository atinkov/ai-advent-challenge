# День 8: Работа с токенами — результаты и выводы

**Дата:** 2026-09-08
**Модель:** qwen3.8-27b @ https://gpustack.data.lmru.tech/v1
**Лимит контекста модели:** 202752 токена (из ответа сервера при переполнении)

## Как считаются токены

| Что | Как | Точность |
|---|---|---|
| Текущий запрос (вместе со всей историей) | поле `usage.prompt_tokens` ответа API | точная |
| Ответ модели | `usage.completion_tokens` | точная |
| Сохранённая история диалога | эвристика: символы / 2.5 (`LlmClient.estimateTokens`) | оценка (в конце сценария 2: 1081 против точных 1140, отклонение ≈ 5 %) |
| Сумма за сессию | накопление `usage` по всем запросам | точная (сумма) |

Агент (`LlmAgent`) отслеживает по каждому запросу: токены запроса/ответа, пиковый размер запроса;
статистика сохраняется в `agent-context.json` (формат v2: `{version, history, stats}`)
и восстанавливается при перезапуске. UI (`Task6`) печатает после каждого хода:

```
[токены: запрос=1140 | ответ=475 | история≈1081 | сессия=12174]
```

## Сценарий 1: короткий диалог (2 хода)

| Ход | Вопрос | Ответ | запрос | ответ | сессия |
|---|---|---|---|---|---|
| 1 | Сколько будет 2+2? | 4 | 47 | 42 | 89 |
| 2 | А теперь 3×3? | 9 | 74 | 29 | 192 |

Запрос вырос с 47 до 74: каждый новый ход отправляет **всю** предыдущую историю заново.

## Сценарий 2: длинный диалог (12 ходов)

Вопросы: «Назови 5 коротких фактов по [физике/химии/биологии/...]».

| Ход | запрос | ответ | история≈ | сессия |
|---|---|---|---|---|
| 1 | 57 | 468 | 99 | 525 |
| 2 | 158 | 509 | 182 | 1192 |
| 3 | 249 | 369 | 280 | 1810 |
| 4 | 356 | 417 | 370 | 2583 |
| 5 | 460 | 450 | 455 | 3493 |
| 6 | 561 | 554 | 555 | 4608 |
| 7 | 667 | 232 | 629 | 5507 |
| 8 | 758 | 302 | 714 | 6567 |
| 9 | 852 | 365 | 800 | 7784 |
| 10 | 950 | 305 | 889 | 9039 |
| 11 | 1050 | 470 | 982 | 10559 |
| 12 | 1140 | 475 | 1081 | 12174 |

Наблюдения:

- **Размер запроса растёт почти линейно**: 57 → 1140 (×20 за 12 ходов, в среднем +95 токенов на ход — это стоимость «среднего» обмена: вопрос + ответ).
- **Суммарные токены сессии растут как сумма арифметической прогрессии** (квадратично): 525 → 12174. Последний запрос — 20-й по размеру от первого.
- Локальная оценка истории (символы/2.5) держится в ≈5 % от точного значения API — годится для мониторинга, не для биллинга.
- Ответы модели были устойчиво короткими (232–554 токена), т.е. рост сессии диктуется именно **переотправлением истории**, а не длиной ответов.

## Сценарий 3: переполнение лимита

Действия: `reset` → сообщение ~1,5 млн символов (~202 753+ токенов) → обычный вопрос → `reset` → обычный вопрос.

1. **Что говорит сервер (HTTP 400, дословно):**

   > This model's maximum context length is 202752 tokens. However, you requested 0 output
   > tokens and your prompt contains at least 202753 input tokens, for a total of at least
   > 202753 tokens. Please reduce the length of the input prompt or the number of requested
   > output tokens. (parameter=input_tokens, value=202753)

2. **Что ломается:**
   - запрос отклонён до инференса (400 BadRequestError, `param=input_tokens`);
   - огромное сообщение **остаётся в истории агента** — следующий, совсем маленький вопрос («А ещё что?») тоже получает 400: промпт уже навсегда превышает лимит. Диалог «отравлен».
   - восстановление — только `reset`: после сброса обычный запрос проходит (запрос=42 | ответ=43).

3. **Как ведёт себя агент:**
   - не завершается и не теряет состояние: `LlmClient.send()` бросает `RequestException`, агент ловит её, печатает ошибку, **диалог не изменяется** (ответа нет — пара user/assistant не создаётся), сессия продолжается;
   - UI подсказывает: «История может превышать лимит модели — попробуйте reset или более короткое сообщение».

## Выводы

1. **Цена диалога растёт быстрее, чем кажется.** Каждый ход пересылает всю историю: размер запроса — линейно, суммарные токены (и деньги, если модель платная) — квадратично. В 12-ходовом диалоге сессия потребила 12174 токена, хотя сами «новые» вопросы и ответы в сумме — меньше трети этого числа.
2. **Стоимость N-го хода ≈ system + N × (средний вопрос + средний ответ).** Для длинных сессий это предсказуемо упирается в лимит контекста (здесь — 202752 токена, т.е. при среднем обмене ~95 токенов/ход «естественный» потолок — порядка 2000 ходов, а с длинными ответами — в десятки раз меньше).
3. **Эвристика символы/2.5** для кириллицы сходится с реальным токенизатором в пределах ≈5 % — подходит для предупреждений «вы приближаетесь к лимиту», не подходит для точного учёта.
4. **Переполнение — необратимо внутри сессии:** сообщение, вызвавшее 400, остаётся в истории и блокирует все последующие запросы. Устойчивый агент должен (а) заранее проверять размер запроса через оценку, (б) при 400 предлагать `reset` или сжатие/резюмирование истории.
5. **Стоимость:** модели этого gpustack-сервера не тарифицируются, поэтому «стоимость» в отчёте — это токены. Для платного API формула: `цена = (prompt + completion) × цена_за_1M / 1_000_000`. Пример: сценарий 2 (12174 токена) при $10 за 1M ≈ **$0.12** за 12-ходовый диалог.

## Как воспроизвести

```bash
rm -f agent-context.json            # чистый старт
mvn -q exec:java -Ptask6            # интерактивно: после каждого хода — строка [токены: ...]
# переполнение: вставьте сообщение > ~200k токенов → 400; следующий вопрос тоже 400; reset → снова работает
```
