# Задание: Остановка и продолжение — сценарий с циклом и зависимыми шагами

## Чему научимся по итогу прохождения урока

* Проектировать сценарий, в котором один и тот же механизм `exitHereIfFailed()` применяется к зависимым шагам, а сознательно не применяется к шагам внутри цикла по независимым элементам, и аргументировать каждое решение.

* Различать сбой, после которого сценарий должен остановиться, и сбой, после которого виртуальный пользователь обязан продолжить работу по оставшимся итерациям цикла, не искажая метрики последующих, не зависящих от него запросов.

* Подтверждать корректность расстановки остановок не на «успешном» прогоне, а нацеленно ломая каждый из кандидатов и читая отчёт Gatling по количеству реально отправленных запросов.

## Требования

Задание выполняется в виде нового сценария в отдельном классе `Simulation`, не затрагивая ранее разработанные сценарии.

1. Реализовать сценарий «Кредитная заявка после серии пополнений» в следующем порядке: авторизация (`/api/v1/auth/login`) → получение списка счетов (`/api/v1/dashboard/accounts`) → цикл по трём первым счетам из полученного списка с выполнением пополнения (`/api/v1/accounts/deposit`) на каждый → получение предложений по кредиту наличными (`/api/v1/loans/cash/offers`) → отправка кредитной заявки (`/api/v1/loans/applications`) → контрольный запрос дашборда (`/api/v1/dashboard`) для подтверждения изменения состояния.

2. Для шагов авторизации, получения списка счетов, получения кредитных предложений и отправки заявки добавить `check(...)` с `exitHereIfFailed()`. Для шага пополнения внутри цикла `exitHereIfFailed()` добавлять **не** следует: неуспех пополнения одного счёта не отменяет необходимость попытаться попополнить два оставшихся. Обоснование каждого решения (добавил / не добавил) фиксируется комментарием в коде непосредственно над соответствующим шагом.

3. В цикле по счетам обеспечить, чтобы при неуспехе `POST /api/v1/accounts/deposit` виртуальный пользователь переходил к следующей итерации, не выполняя дополнительных запросов для «упавшего» счёта. Конкретный механизм (условная ветка, `onError`, игнорирование кода ответа) выбирается самостоятельно, но в отчёте Gatling по шагу пополнения должны быть видны как зелёные, так и красные запросы при частичном сбое.

4. Подготовить три намеренных сбоя для верификации: (а) невалидный логин/пароль на этапе авторизации; (б) временный «отказ» на эндпоинте пополнения (например, сумма, гарантированно отклоняемая API, но не ломающая соединение); (в) невалидный токен на этапе запроса кредитных предложений. Для каждого сбоя выполнить прогон с одним виртуальным пользователем и сохранить отчёт.

5. В комментарии в коде класса `Simulation` (блок-комментарий в начале файла) кратко описать, какие именно последующие шаги делают бессмысленными при неуспехе каждого из четырёх шагов, к которым добавлен `exitHereIfFailed()`, и почему в шаге пополнения внутри цикла остановка не оправдана.

## Критерии успешного прохождения

* В отчёте прогона с невалидными учётными данными видно ровно один отправленный запрос (авторизация) и ни одного последующего: дашборд, пополнения, кредитные предложения, заявка и контрольный запрос не выполняются.
* В отчёте прогона с «отказом» на пополнении видно, что виртуальный пользователь отправил запросы на пополнение ко всем трём счетам (хотя бы два из трёх завершились успешно), а затем выполнил запрос кредитных предложений, заявку и контрольный дашборд — цикл не прервался на первой итерации.
* В отчёте прогона с невалидным токеном на кредитных предложениях видно, что авторизация, дашборд и три пополнения выполнены, а запросы на кредитную заявку и контрольный дашборд отсутствуют.
* В коде каждого из четырёх шагов с `exitHereIfFailed()` присутствует как минимум одна содержательная `check(...)` (код ответа и/или поле тела), а не только `status().is(200)`.
* Комментарий-обоснование в начале класса ссылается на конкретные последующие шаги по имени эндпоинта, а не на абстрактное «всё сломается».

## Подсказки

* В уроке обратите внимание на раздел, где рассматривается разграничение «зависимый шаг» и «независимый элемент цикла»: критерий — используется ли результат текущего шага при **построении тела** или **выборе ветки** последующего запроса. Если да — остановка оправдана; если последующие итерации цикла работают с другими сущностями — нет.
* Для намеренного сбоя на пополнении не нужно менять код API: достаточно передать сумму, которую демо-стенд отклонит с бизнес-ошибкой (например, 0 или отрицательное значение), — соединение при этом остаётся живым, и Gatling корректно фиксирует неуспех без сетевых исключений.
* При проверке отчёта смотрите не только на общую долю OK/KO, а на **количество отправленных запросов** по каждому эндпоинту: именно оно показывает, остановился ли виртуальный пользователь на нужном шаге или продолжил.
