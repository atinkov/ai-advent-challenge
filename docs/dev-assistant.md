# Ассистент разработчика (день 31)

CLI-ассистент, который отвечает на вопросы о проекте AIAdventChallenge. Знания берёт из двух мест:

1. **Документация (RAG)** — `README.md`, всё из `docs/` (архитектура, схемы данных, описания API) и `AGENTS.md`.
2. **Репозиторий (MCP)** — собственный MCP-сервер `project-mcp-server` (`week7/ProjectMcpServer`): текущая ветка, статус, файлы, diff.

## Запуск

```bash
mvn -q compile exec:java -Ptask31                                          # автопроверка задания по условию → task31-dev-assistant-report.md
mvn -q exec:java -Ptask31 -Dexec.args="chat"                              # интерактивный режим, приглашение dev>
mvn -q exec:java -Ptask31 -Dexec.args="/help где лежат схемы данных?"      # одна команда и выход
mvn -q exec:java -Ptask31 -Dexec.args="/branch"
```

## Автопроверка задания

Запуск без аргументов (или `check`) проверяет задание по трём условиям через те же пути, что использует разработчик
(диспетчер команд, MCP-сервер по stdio, реальный индекс), и пишет вердикт «задание выполнено / не выполнено» в `task31-dev-assistant-report.md`:

1. **RAG по документации** — `README.md` в индексе; все файлы `docs/` в индексе (сверка с диском); есть схемы данных или API-описания; поиск по вопросу о структуре находит README/docs.
2. **MCP** — handshake; в `tools/list` есть `git_current_branch`; ветка из `/branch` совпадает с `git branch --show-current`; по желанию — `/files` и `/diff`.
3. **`/help`** — справка без аргументов; три обязательных вопроса: структура проекта (ответ со ссылками на README/docs), текущая ветка + правило именования (ветка из MCP в ответе), незакоммиченные файлы (модель сама вызывает MCP `git_status`/`git_diff`). Ещё три дополнительных вопроса (схема данных, API, вопрос не по теме) в вердикт не входят.

Без `LLM_API_KEY` условие 3 не выполняется — ответы модели проверить нельзя.

Без `LLM_API_KEY` ассистент тоже запускается: `/branch`, `/status`, `/files`, `/diff`, `/docs` работают, а `/help <вопрос>`
показывает найденные фрагменты документации без ответа модели.

## Команды

| Команда | Что делает |
|---|---|
| `/help` | список команд и откуда ассистент берёт знания (группы документации, текущая ветка) |
| `/help <вопрос>` | ответ на вопрос о проекте: RAG по документации + текущая ветка из MCP + инструменты MCP по решению модели |
| `<вопрос>` | то же, что `/help <вопрос>` |
| `/branch` | текущая ветка, HEAD, upstream, впереди/позади (MCP `git_current_branch`) |
| `/status` | staged / modified / untracked (MCP `git_status`) |
| `/files [маска\|папка]` | файлы проекта под git с учётом `.gitignore` (MCP `list_files`), например `/files docs/**`, `/files src/main/java/ru/lemanapro/aiadventchallenge/week7` |
| `/diff [путь]` | незакоммиченный diff (MCP `git_diff`) |
| `/docs` | состав базы знаний: файл, группа, число фрагментов |
| `/reindex` | принудительно перестроить индекс документации |
| `/tools` | инструменты MCP-сервера проекта |
| `/exit` | выход |

## Как отвечает `/help <вопрос>`

1. Приложение само вызывает MCP `git_current_branch` — ветка попадает в промпт всегда (это минимум задания).
2. `ProjectDocs.retrieve` ищет фрагменты документации: косинус top-20 → отсечка `score ≥ max(TASK31_MIN_SCORE, TASK31_RELATIVE_CUT × лучший)` →
   не больше `TASK31_PER_SOURCE` фрагментов из одного файла → top `TASK31_TOP_K` (5).
3. `McpToolAgent` (общий агент недели 4) отправляет модели system prompt + сообщение «ветка + фрагменты [1..N] + вопрос».
   Если вопрос о текущем состоянии («что я поменял», «какие файлы в docs») — модель сама вызывает `git_status` / `list_files` / `git_diff`.
4. В ответе модель ставит ссылки `[n]`. Ссылки проверяются в коде: учитываются только номера фрагментов, которые были в промпте,
   остальные отбрасываются с предупреждением. Список «Источники» печатается из метаданных индекса (файл › раздел, строки), а не из текста модели.
5. Если ответа нет ни в документации, ни в инструментах — ассистент говорит «В документации проекта этого нет».

## Индекс документации

- Файл `task31-docs-index.json` + `task31-docs-index.json.sha256` (оба в `.gitignore`).
- Пересобирается автоматически, если изменился любой файл документации (sha256 по путям и содержимому) или настройки эмбеддингов.
- Эмбеддер — как в неделе 5: модель по API (`EMBEDDING_*`), а если она недоступна — локальный `local-hash-2048`.
- Нарезка — структурная (`Chunker.structure`): Markdown по заголовкам, JSON/YAML по абзацам, максимум `TASK31_CHUNK_MAX` (1500) символов.

## Переменные окружения

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `TASK31_REPO` | `.` | корень проекта (репозиторий для MCP и корень документации) |
| `TASK31_DOC_PATHS` | `README.md,docs,AGENTS.md` | что индексировать (файлы и папки через запятую) |
| `TASK31_INDEX` | `task31-docs-index.json` | файл индекса |
| `TASK31_TOP_K` | `5` | фрагментов в промпте |
| `TASK31_PER_SOURCE` | `2` | максимум фрагментов из одного файла |
| `TASK31_MIN_SCORE` | `0.3` (API) / `0.08` (local-hash) | абсолютный порог косинуса |
| `TASK31_RELATIVE_CUT` | `0.6` | относительный порог от лучшего результата |
| `TASK31_CHUNK_MAX` | `1500` | максимальный размер фрагмента |
| `TASK31_TOOL_MODE` | `auto` | `auto` / `native` / `prompt` — как модель вызывает MCP-инструменты |

## Классы

| Класс | Роль |
|---|---|
| `week7/Task31` | CLI: команды, интерактивный режим, `check` + отчёт |
| `week7/DevAssistant` | MCP-клиент к серверу проекта + RAG + LLM-агент; проверка ссылок |
| `week7/ProjectDocs` | корпус документации, индекс с автопересборкой, поиск |
| `week7/ProjectMcpServer` | stdio MCP-сервер: `git_current_branch`, `git_status`, `list_files`, `git_diff` (только чтение) |

Чтобы ассистент знал о новой части проекта, достаточно описать её в `README.md` или в `docs/` — индекс пересоберётся при следующем запуске.
