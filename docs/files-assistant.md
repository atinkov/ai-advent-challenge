# Ассистент для работы с файлами проекта (день 34)

Ассистент получает цель словами («найди все места…», «проверь курс на соответствие правилам…», «сгенерируй README…»),
сам решает, какие файлы смотреть, и работает с ними через MCP: читает, ищет по нескольким файлам, анализирует ссылки и
историю git, создаёт и правит файлы. Результат — ответ + unified diff всех изменений (применяется `git apply`).

По умолчанию проект — репозиторий курса `lmru--qacc--performance-qa-course`, лежащий рядом с этим репозиторием;
другой проект — `TASK34_ROOT` или `--root <папка>`.

| Часть | Где | Что делает |
|---|---|---|
| Файлы проекта | `week7/ProjectFiles` | песочница над корнем проекта: пути только внутри корня, без `.git`/`.idea`/`target`/`.env`; список, чтение с номерами строк, поиск (строка/regex, `files_without`), анализ Markdown-ссылок, `git log`; изменения копятся в оверлее и отдаются как unified diff (LCS по строкам, 3 строки контекста, совместим с `git apply`) |
| MCP-сервер | `week7/ProjectFilesMcpServer` | stdio-сервер `project-files-mcp-server` над `ProjectFiles`; режим dry-run (по умолчанию) или `--apply` — запись на диск |
| Ассистент | `week7/FilesAssistant` | общий `week4/McpToolAgent` (цикл tool calling, до `TASK34_MAX_STEPS` = 30 шагов) + системный промпт «сначала структура и поиск, факты только из инструментов, точечные правки, check_links и pending_changes перед ответом»; каждый вызов записывается — хост знает, какие файлы прочитаны / найдены / изменены |
| Интерфейс и проверка | `week7/Task34` | одна цель, чат, 4 сценария с проверками в коде → `task34-files-assistant-report.md`, `task34-output/*.patch` |

## Инструменты MCP

| Инструмент | Параметры | Что делает |
|---|---|---|
| `list_files` | `glob` | файлы проекта с числом строк; `*.md` — по имени в любой папке, имя папки — всё в ней |
| `read_file` | `path`*, `start_line`, `end_line` | текст с номерами строк, до 250 строк за раз |
| `search` | `query`*, `regex`, `glob`, `case_sensitive`, `files_without`, `max_results` | совпадения `путь:строка: текст` + число по файлам; `files_without=true` — файлы, где запроса нет |
| `check_links` | `glob` | битые относительные ссылки и .md-файлы, на которые никто не ссылается |
| `git_log` | `limit`, `path`, `with_files` | история git (только чтение) |
| `write_file` | `path`*, `content`* | создать / перезаписать текстовый файл, вернуть diff |
| `edit_file` | `path`*, `old_text`*, `new_text`*, `replace_all` | точечная замена фрагмента (ровно одно вхождение), вернуть diff; при промахе — подсказка с похожей строкой |
| `pending_changes` | — | все изменения сессии: сводка + unified diff |

Чтение и поиск видят несохранённые изменения — после правки `check_links` проверяет уже новую версию.

## Запуск

```bash
mvn -q compile exec:java -Ptask34                                                  # 4 сценария + проверки → task34-files-assistant-report.md
mvn -q exec:java -Ptask34 -Dexec.args="chat"                                      # интерактивно: files> цель | /diff | /save | /tools | /exit
mvn -q exec:java -Ptask34 -Dexec.args="Найди все места, где используется feed"   # одна цель, dry-run → task34-output/goal-*.patch
mvn -q exec:java -Ptask34 -Dexec.args="--apply Сгенерируй CHANGELOG.md по истории git"  # то же с записью в файлы проекта
mvn -q exec:java -Ptask34 -Dexec.args="--root ../другой-проект chat"              # любой другой проект
mvn -q exec:java -Ptask34 -Dexec.args="tools"                                     # инструменты MCP-сервера, без LLM
git -C ../lmru--qacc--performance-qa-course apply ../AIAdventChallenge/task34-output/s3-readme.patch   # применить diff
```

Переменные: `TASK34_ROOT`, `TASK34_TOOL_MODE` (auto | native | prompt), `TASK34_MAX_STEPS` (30),
`TASK34_ONLY` (например `s1,s3` — перезапустить часть сценариев: результат каждого лежит в `task34-output/sN-result.json`,
отчёт собирается из всех сохранённых), `TASK34_THINK` (`off`/`on` — переключатель размышлений Qwen3 на vLLM; по умолчанию
как решит сервер: без размышлений qwen3.8-27b зацикливался на поиске), `LLM_TIMEOUT_SECONDS` (120 — один запрос к LLM);
LLM — как у всех дней (`LLM_API_KEY`, `HINDSIGHT_API_LLM_*` в `.env`). На Linux запускать с `LC_ALL=C.UTF-8` (кириллица в именах файлов).

## Сценарии проверки (`check`)

Цели сформулированы как задачи — ни одна не называет существующий файл. Проверка всегда в dry-run: курс на диске не меняется
(`git status` до и после сравнивается), результат каждого сценария — patch в `task34-output/`.

| # | Цель | Эталон / проверки в коде |
|---|---|---|
| s1 | найти все места, где используется `exitHereIfFailed` | тот же поиск в `ProjectFiles` даёт 10 файлов — все должны быть в ответе; ассистент искал сам и ничего не менял |
| s2 | проверить правила навигации, описанные в самом курсе (всё доступно из общего списка уроков, ссылки рабочие), исправить | правила в коде: каждый .md в подпапке есть в «Карте курса», нет битых ссылок; нарушение (инструкция по окружению не в карте) упомянуто в ответе и исправлено diff-ом; правки точечные |
| s3 | создать README.md: модули с числом уроков и заданий, с чего начать | все модули, числа совпадают с файлами, ссылки рабочие, есть ссылки на карту курса и инструкцию |
| s4 | CHANGELOG.md по истории git | все коммиты (по хешу) и даты, нет выдуманных хешей, даты по убыванию |

Для каждого сценария также: ≥ 3 вызовов инструментов, нужное число файлов «в работе» (прочитаны / найдены / изменены),
`git apply --check` принимает сохранённый patch, `git status` проекта не изменился.

Устойчивость: если модель закончила пустым сообщением (только размышления), упёрлась в лимит шагов или запрос к LLM
оборвался по таймауту, `FilesAssistant` продолжает тот же диалог (до 2 раз) — уже полученные результаты инструментов не теряются.

## Результат прогона

`task34-files-assistant-report.md` — qwen3.8-27b, все 4 сценария ✅ (25–45 с каждый):
s1 нашёл все 10 файлов с `exitHereIfFailed` и объяснил назначение по строкам; s2 нашёл, что инструкция по развёртыванию
окружения недоступна из «Карты курса», и добавил её туда (+4 строки); s3 создал README с таблицей модулей (числа совпали
с файлами во всех 8 модулях); s4 собрал CHANGELOG из всех 30 коммитов по датам и модулям. Diff-ы — в `task34-output/`.

Почему так: ассистенту дан общий файловый инструментарий, а не «инструмент под задачу»; эталоны считаются тем же `ProjectFiles`,
что видит модель, поэтому проверка не зависит от текста ответа там, где можно проверить результат (diff, итоговые файлы).
