### alexey — код=✗, java-признаки=✗, объясн. тон=✗, длина=1518 симв.

> Индекс = B+tree/hash/GIN структура для ускорения поиска по столбцу(ам). Смысла повторять, что это такое, нет — ты и так знаешь. Давай по делу: **когда ставим, а когда нет**.
> 
> **Ставим:**
> - `WHERE`, `JOIN`, `ORDER BY`, `GROUP BY` по столбцу с высокой селективностью (>1% строк на значение).
> - Покрытие: `SELECT a, b FROM t WHERE a = ?` — индекс на `(a, b)` убирает lookup в heap.
> - Partial index: `WHERE status = 'active'` у 90% строк → `CREATE INDEX ... WHERE status = 'active'` — меньше размер, быстрее maintenance.
> - BRIN на последовательных данных (timestamp, id с автоинкрементом) — на порядки компактнее B-tree.
> 
> **Не ставим / уберём:**
> - Колонка с низкой селективностью (`gender`, `is_deleted` с 0.1% null) — planner всё равно сканит.
> - Малая таблица (< пары тысяч строк) — seq scan быстрее.
> - Частые `INSERT/UPDATE` на hot-таблице: каждый индекс = extra write amplification. Считай: 5 индексов × 10k TPS = +50k b-tree modifications/s.
> - Индекс на столбце, по которому фильтруют `< 5%` строк, но при этом `EXPLAIN ANALYZE` показывает seq scan + filter дешевле.
> 
> **Практика:**
> 1. `EXPLAIN (ANALYZE, BUFFERS)` → смотри `actual rows` vs `rows` (planner estimate). Разница >10× → обновлять `ANALYZE`.
> 2. Partial/covering вместо «ещё один B-tree».
> 3. `pg_stat_user_indexes`: `idx_scan = 0` за месяц → кандидат на удаление.
> 4. Composite: порядок столбцов = порядок предикатов + селеktiviti. `(status, created_at)` ≠ `(created_at, status)`.
> 
> Если нужно под конкретный кейс — кидай схему + запросы, разберу по `EXPLAIN`.

> # Индекс в базе данных — пошаговое объяснение
> 
> Привет, Игорь! Отличный вопрос — индексы это один из тех тем, которые на собеседованиях спрашивают почти всегда, а на практике без них база начинает «тормозить» уже при сотнях тысяч строк. Разберём по шагам.
> 
> ---
> 
> ## Шаг 1. Аналогия, чтобы «в голове встало»
> 
> Представь толстую энциклопедию на 1000 страниц.
> 
> - **Без индекса** (то, что в БД называют **полным сканированием** — full table scan): чтобы найти слово «база данных», ты листаешь страницу за страницей от начала до конца. В таблице на 1 000 000 строк это 1 000 000 проверок.
> - **С индексом**: ты открываешь оглавление в конце книги, видишь «база данных — стр. 342», и идёшь прямо туда. Проверок — пара.
> 
> Индекс в базе данных — это **отдельная структура данных**, которая хранит отсортированную «шпаргалку» с ключами и указателями на строки в основной таблице. За счёт этого поиск идёт не за O(n), а за O(log n).
> 
> > **O(log n)** — это оценка сложности (как быстро вырастает время при росте данных). При 1 000 000 строк log₂(1 000 000) ≈ 20. То есть вместо миллиона сравнений — около 20.
> 
> ---
> 
> ## Шаг 2. Как это устроено внутри (кратко)
> 
> Большинство СУБД (PostgreSQL, MySQL/InnoDB, Oracle) используют **B-дерево** (B-tree):
> 
> - Это дерево, в котором каждый узел хранит несколько ключей и «веток» вниз.
> - Дерево всегда **отсортировано** и **сбалансировано** (все листья на одной высоте).
> - Чтобы найти значение, движок БД спускается от корня к листу, на каждом узле отбрасывая «не те» ветви.
> 
> Типы индексов, которые стоит знать как джуниору:
> 
> | Тип | Когда применять |
> |-----|----------------|
> | **B-Tree** (по умолчанию) | Равенство, диапазоны, сортировка. Самый универсальный. |
> | **HASH** | Только точное совпадение (`WHERE id = 42`). Быстрее B-tree на точных совпадениях, но не работает для `<`, `>`, `LIKE 'ab%'`. |
> | **Gin / Gist** (PostgreSQL) | Полнотекстовый поиск, массивы, геометрия. |
> | **Partial** (частичный) | Индексируем только часть строк, например `WHERE status = 'active'`. Экономит место. |
> 
> ---
> 
> ## Шаг 3. Когда индекс **стоит** создавать
> 
> 1. **Частые `WHERE` по этому столбцу.**
>    Если в запросе `WHERE email = ...` встречается в 80% запросов к таблице — да, индекс на `email`.
> 
> 2. **Столбцы в `JOIN`.**
>    Если таблица `orders` joinится с `customers` по `customer_id` — индекс на `orders.customer_id` ускорит сборку строк.
> 
> 3. **Столбцы в `ORDER BY` / `GROUP BY`.**
>    Без индекса БД должна «разложить» результат в оперативную память и отсортировать (external sort). С индексом — уже отсортировано.
> 
> 4. **Уникальность.**
>    `UNIQUE INDEX` одновременно и индексирует, и запрещает дубликаты. Например, `email` в таблице пользователей.
> 
> 5. **Комбинированные (composite) индексы.**
>    Если часто ищешь `WHERE city = 'Москва' AND street = 'Ленина'`, индекс `(city, street)` будет быстрее двух отдельных.
> 
> ---
> 
> ## Шаг 4. Когда индекс **не стоит** создавать
> 
> - **Таблица маленькая** (до ~1000 строк). Full scan и так за миллисекунды.
> - **Столбец с очень низким «разновидом»** (cardinality): например, `gender` — всего 2 значения. Индекс почти не фильтрует.
> - **Частые INSERT / UPDATE / DELETE.**
>   Каждый индекс нужно **поддерживать** при каждом изменении данных. 5 индексов на столбце, который обновляется в каждой транзакции, — это 5 лишних записей в индексе на каждую запись в таблице.
> - **Столбец, который вы почти никогда не используете в фильтрах.**
> 
> ---
> 
> ## Шаг 5. Пример на Java + JPA / Hibernate
> 
> Покажу, как объявить индексы через аннотации и как проверить их через SQL.
> 
> ### 5.1. Сущность (entity) с индексами
> 
> ```java
> // Пакет: com.example.model
> import jakarta.persistence.*;
> import java.time.LocalDate;
> 
> // @Entity — говорит Hibernate, что этот класс соответствует таблице в БД
> @Entity
> // @Table — имя таблицы в базе; indexes описывают, какие индексы создать
> @Table(
>     name = "orders",                          // имя таблицы
>     indexes = {
>         // Индекс по клиенту: ускорит WHERE customer_id = ?
>         @Index(name = "idx_orders_customer",   // уникальное имя индекса
>                columnList = "customer_id"),    // по какому столбцу
> 
>         // Композитный индекс: ускорит WHERE status = ? AND created_at > ?
>         @Index(name = "idx_orders_status_date",
>                columnList = "status, created_at")
>     },
>     uniqueConstraints = {
>         // UNIQUE-индекс: номер заказа не повторяется
>         @UniqueConstraint(name = "uq_order_number",
>                           columnNames = "order_number")
>     }
> )
> public class Order {
> 
>     // Первичный ключ — на него индекс создаётся АВТОМАТИчески
>     @Id
>     @GeneratedValue(strategy = GenerationType.IDENTITY) // автоинкремент
>     private Long id;
> 
>     // Внешний ключ на таблицу customers
>     private Long customerId;
> 
>     // Статус: "NEW", "PAID", "SHIPPED", "CANCELLED"
>     private String status;
> 
>     // Уникальный номер заказа
>     private String orderNumber;
> 
>     // Дата создания
>     private LocalDate createdAt;
> 
>     // ... геттеры и сеттеры (для краткости опущены)
> }
> ```
> 
> > **Что происходит при старте приложения?** Hibernate (в режиме `ddl-auto = update`) сгенерирует SQL вроде:
> > ```sql
> > CREATE INDEX idx_orders_customer ON orders (customer_id);
> > CREATE INDEX idx_orders_status_date ON orders (status, created_at);
> > CREATE UNIQUE INDEX uq_order_number ON orders (order_number);
> > ```
> 
> ### 5.2. Как убедиться, что индекс реально «сработал»
> 
> В PostgreSQL:
> 
> ```java
> // Пакет: com.example.repo
> import org.springframework.data.jpa.repository.JpaRepository;
> import org.springframework.data.jpa.repository.Query;
> import org.springframework.data.repository.query.Param;
> import java.util.List;
> import java.time.LocalDate;
> 
> public interface OrderRepository extends JpaRepository<Order, Long> {
> 
>     // Простой запрос: Hibernate сам подставит WHERE customer_id = ?
>     // Если idx_orders_customer существует — БД использует seek, а не full scan
>     List<Order> findByCustomerId(Long customerId);
> 
>     // Комбинированный запрос — попадёт в композитный индекс
>     @Query("""
>         SELECT o FROM Order o
>         WHERE o.status = :status
>           AND o.createdAt > :since
>         ORDER BY o.createdAt DESC
>         """)
>     List<Order> findActive(@Param("status") String status,
>                            @Param("since") LocalDate since);
> }
> ```
> 
> ### 5.3. Проверка в psql / DBeaver
> 
> ```sql
> -- Посмотрим план выполнения запроса
> EXPLAIN ANALYZE
> SELECT * FROM orders WHERE customer_id = 42;
> ```
> 
> В выводе ищи строку:
> 
> ```
> Index Scan using idx_orders_customer on orders
> ```
> 
> Если видишь `Seq Scan on orders` — значит, индекс **не** используется (слишком мала таблица или статистика устарела).
> 
> ---
> 
> ## Шаг 6. Чек-лист для практики (закрепи)
> 
> 1. **Начни с `EXPLAIN`** — не гадай, смотри план.
> 2. **Один индекс на один запрос.** Не «на всякий случай» пять индексов.
> 3. **Смотри на SELECT-и и JOIN-и** в своих репозиториях — где `WHERE`, там и кандидат.
> 4. **Не индексируй** столбцы, которые ты сам никогда не фильтруешь.
> 5. **На больших таблицах** (> 100 тыс. строк) создавай индексы в off-peak время — `CREATE INDEX` блокирует запись на время построения (в PostgreSQL есть `CREATE INDEX CONCURRENTLY` — не блокирует).
> 6. **Чисть мёртвые индексы**: если столбец больше не используется в фильтрах — `DROP INDEX`.
> 
> ---
> 
> ## Шаг 7. Частая ошибка джуниора
> 
> > «Я добавил индекс на `email` — почему запрос всё равно медленный?»
> 
> Возможные причины:
> - В запросе `WHERE LOWER(email) = ?` — функция над столбцом **обходит** обычный индекс. Решение: индекс по `LOWER(email)` (functional index в PostgreSQL) или хранить `email` в одном регистре.
> - В `WHERE` есть и `email`, и `status`, а индекс только по `email`. БД находит строки по email, но всё равно сканирует по status. Решение: композитный индекс `(email, status)`.
> - Данные не обновлялись с момента последнего `ANALYZE` — статистика устарела, планировщик «решил», что full scan дешевле. Решение: `ANALYZE orders;`.

### alexey — код=✓, java-признаки=✗, объясн. тон=✗, длина=2294 симв.

> Алгоритм (без EXPLAIN угадывать нечего):
> 
> **1. Диагностика**
> ```sql
> EXPLAIN (ANALYZE, BUFFERS, TIMING, FORMAT TEXT)
> SELECT ... FROM users WHERE ...;
> ```
> Смотрим: `Seq Scan` на 1M строк? `Actual rows` << `rows`? `Buffers: shared hit/read` — read > 0 = ходит на диск.
> 
> **2. Типовые причины и фиксы**
> 
> | Симптом в EXPLAIN | Причина | Фикс |
> |---|---|---|
> | Seq Scan + Filter | Нет индекса / низкая селективность | Partial index, covering index |
> | Index Scan + Heap Fetch (много) | Index-only scan не работает (visibility map dirty) | `VACUUM` + `INDEX ONLY` в запросе |
> | Nested Loop, inner = 1M | Ошибка planner'а (устаревший statistics) | `ANALYZE users` |
> | Sort (top-N heapsort / external merge) | Нет индекса под `ORDER BY` | Composite index: `(sort_col, filter_col)` |
> | Hash Join на 1M × 1M | Нет индекса на join-колонке | B-tree на FK |
> | `Buffers: shared read` в сотнях | Working set > shared_buffers | Увеличить `shared_buffers` / `effective_cache_size` |
> 
> **3. По самому запросу**
> 
> - `SELECT *` → только нужные колонки (покрытие индексом).
> - `LIKE '%foo'` → FTS (`to_tsvector`) или pg_trgm GIN.
> - `NOT IN (subquery)` → `NOT EXISTS` или `LEFT JOIN ... IS NULL`.
> - `OFFSET 100000` → ключевая пагинация: `WHERE (created_at, id) < (?, ?) ORDER BY ... LIMIT 50`.
> - `COUNT(*)` на 1M — если допустимо приближённое: `pg_class.reltuples`, иначе материализованная счётная таблица / Redis.
> 
> **4. Индексы (пример)**
> ```sql
> -- частый фильтр + сортировка + покрытие
> CREATE INDEX idx_users_status_created 
>   ON users (status, created_at DESC) 
>   INCLUDE (email, name);
> 
> -- partial: только active
> CREATE INDEX idx_users_active_email 
>   ON users (email) 
>   WHERE is_deleted = false;
> ```
> 
> **5. Java-сторона** (если не оптимизировано)
> - PreparedStatement pool (HikariCP по дефту).
> - Батчинг: `rewriteBatchedStatements=true` в JDBC URL для PG/MySQL.
> - N+1: один запрос с `JOIN` / `IN` вместо цикла. Если JPA — `@EntityGraph` или QueryDSL с fetch join.
> - Не тащить 1M строк: `setFetchSize(500)` + cursor (PG) / stream (MySQL `useCursorFetch=true`).
> 
> **6. Структурное** (если 1M — это потолок, а не норма)
> - Партиционирование по `created_at` (RANGE) — старые куски в cold storage.

> # Оптимизация медленного SQL-запроса к таблице `users` (1 000 000 строк)
> 
> Привет, Игорь! Давай разберём **пошаговый процесс**, который ты можешь применять каждый раз, когда видишь «запрос висит 5 секунд». Не будем гадать — будем **диагностировать → фиксировать → проверять**.
> 
> ---
> 
> ## Шаг 1. Диагностика: найди «узкое горло»
> 
> Прежде чем что-то менять, **увиди**, что именно тормозит.
> 
> ### 1.1. Включи `EXPLAIN ANALYZE`
> 
> Это команда, которая показывает **план выполнения** запроса (какой порядок операций БД выбрала) и **реальное время** на каждом шаге.
> 
> Открой psql / DBeaver и выполни свой запрос через `EXPLAIN ANALYZE`:
> 
> ```sql
> -- Пример "медленного" запроса: ищем пользователей по имени, городу и дате регистрации
> EXPLAIN ANALYZE
> SELECT id, full_name, email, city, created_at
> FROM users
> WHERE full_name LIKE 'Иван%'
>   AND city = 'Казань'
>   AND created_at > '2024-01-01'
> ORDER BY created_at DESC
> LIMIT 50;
> ```
> 
> ### 1.2. Что читать в выводе
> 
> | Строка в плане | Что значит |
> |---|---|
> | `Seq Scan on users` | **Полное сканирование** (full scan) — БД читает все 1 000 000 строк. При 1M строк — это ~1–5 секунд. |
> | `Index Scan using ...` | Индекс используется — хорошо. |
> | `Sort Method: external merge` | БД не смогла отсортировать в оперативной памяти и пролила на диск. Дорого. |
> | `Filter: (full_name ~~ 'Ivan%'::text)` | Фильтрация **после** скана — индекс не помог. |
> | `Rows Removed by Filter: 998000` | Из 1M строк 998 000 выброшены фильтром — индекс должен был отфильтровать **до** скана. |
> 
> > **Внешняя сортировка** (external merge sort) — когда данных больше, чем `work_mem` (размер оперативной памяти, выделенной на сортировку), БД пишет временные файлы на диск. Это в 10–50 раз медленнее сортировки в RAM.
> 
> ### 1.3. Частый «приговор» для 1M строк
> 
> Скорее всего ты увидишь:
> 
> ```
> Limit  (cost=0.00..4523.12 rows=50)
>   ->  Sort  (cost=4473.12..4473.24 rows=50)     ← сортировка ВСЕХ совпавших строк
>         Sort Method: top-N heapsort  Memory: 24kB
>         ->  Seq Scan on users  (cost=0.00..4473.12 rows=50)  ← FULL SCAN!
>               Filter: ((full_name ~~ 'Ivan%'::text) AND (city = 'Казань'::text) ...)
>               Rows Removed by Filter: 997450     ← 99.7% строк выброшено
> ```
> 
> **Вывод:** БД сканирует миллион строк, потому что **нет подходящего индекса**.
> 
> ---
> 
> ## Шаг 2. Фикс: создай правильный индекс
> 
> ### 2.1. Какой индекс нужен?
> 
> Посмотри на `WHERE`:
> 
> ```sql
> WHERE full_name LIKE 'Иван%'   -- префиксное совпадение → обычный B-tree ПОДХОДИТ
>   AND city = 'Казань'          -- точное равенство
>   AND created_at > '2024-01-01' -- диапазон
> ORDER BY created_at DESC       -- сортировка
> ```
> 
> Ключевое правило: **порядок столбцов в композитном индексе** должен соответствовать порядку условий:
> 
> 1. Столбцы с **`=**` (равенство) — **первыми**.
> 2. Столбцы с **префиксным LIKE `'abc%'`** — как равенство (B-tree понимает префикс).
> 3. Столбцы с **диапазоном** (`>`, `<`, `BETWEEN`) — **последними** (после них B-tree не может продолжать бинарный поиск по следующим столбцам).
> 
> Итак:
> 
> ```sql
> -- Индекс: (city, full_name, created_at)
> -- city       — точное равенство → первый
> -- full_name  — префикс → второй
> -- created_at — диапазон + ORDER BY → третий (и заодно убивает сортировку!)
> CREATE INDEX idx_users_city_name_date
>     ON users (city, full_name, created_at);
> ```
> 
> > **Почему `city` первый, а не `full_name`?**
> > Если бы порядок был `(full_name, city, created_at)`, то при `WHERE city = 'Казань'` индекс **не мог бы** использовать `city` как первый столбец (правило **leftmost prefix** — левый префикс: B-tree использует столбцы строго по порядку слева направо). А вот `(city, full_name, created_at)` работает идеально: фиксируем `city`, дальше сузиваем по `full_name`, дальше `created_at` даёт и фильтр, и порядок.
> 
> ### 2.2. Проверь результат
> 
> ```sql
> ANALYZE users;  -- обновить статистику, чтобы планировщик "увидел" новый индекс
> 
> EXPLAIN ANALYZE
> SELECT id, full_name, email, city, created_at
> FROM users
> WHERE full_name LIKE 'Иван%'
>   AND city = 'Казань'
>   AND created_at > '2024-01-01'
> ORDER BY created_at DESC
> LIMIT 50;
> ```
> 
> Теперь ожидаешь:
> 
> ```
> Limit  (cost=0.29..1.87 rows=50)
>   ->  Index Scan using idx_users_city_name_date on users
>         Index Cond: (city = 'Казань'::text AND full_name >= 'Ivan' AND full_name < 'Ivaq')
>         Filter: (created_at > '2024-01-01')
> ```
> 
> **Seq Scan пропал.** Время: с ~3 сек → ~2 мс.

> ## Шаг 3. Другие типичные «замедлители» и их фикс
> 
> Помимо отсутствия индекса, вот ещё 5 причин, почему запрос на 1M строк тормозит:
> 
> ### 3.1. SELECT * — берёшь все 30 столбцов, а нужны 5
> 
> ```sql
> -- ПЛОХО: читает всю строку с диска (wide row)
> SELECT * FROM users WHERE ...;
> 
> -- ХОРОШО: только нужные столбцы (covers index → "index-only scan")
> SELECT id, full_name, email, city, created_at FROM users WHERE ...;
> ```
> 
> > **Index-only scan** — если все запрашиваемые столбцы уже есть в индексе, БД **вообще не идёт** в таблицу. Читает только индексы (они компактнее).
> 
> ### 3.2. Функция над столбцом в WHERE
> 
> ```sql
> -- ПЛОХО: индекс на email не сработает, т.к. БД применяет функцию К СТРОКЕ из таблицы
> SELECT * FROM users WHERE LOWER(email) = 'ivan@yandex.ru';
> 
> -- РЕШЕНИЕ 1: индекс по выражению (PostgreSQL 11+)
> CREATE INDEX idx_users_email_lower ON users (LOWER(email));
> 
> -- РЕШЕНИЕ 2 (лучше): храни email в едином регистре, и тогда LOWER() не нужен
> ```
> 
> ### 3.3. N+1 в Hibernate
> 
> Это **самая частая** причина «медленного запроса» на Java-стороне. Не один SQL, а 1 + N:
> 
> ```java
> // ПЛОХО: один запрос на orders + N запросов на users (по одному на каждый order)
> @OneToMany(fetch = FetchType.LAZY)
> private List<User> users; // при доступе k.getOrder().getUsers() — отдельный SELECT
> ```
> 
> На 1 000 000 строк это 1 000 001 запрос. **Решение:**
> 
> ```java
> // Вариант 1: EAGER для маленьких коллекций (осторожно!)
> @OneToMany(fetch = FetchType.EAGER)
> private List<User> users;
> 
> // Вариант 2 (правильнее): explicit JOIN FETCH в репозитории
> @Query("SELECT o FROM Order o JOIN FETCH o.users WHERE o.id = :id")
> OrderDto findByIdWithUsers(@Param("id") Long id);
> 
> // Вариант 3: DTO-проекция — не тяни entity вообще
> @Query("SELECT NEW com.example.dto.UserBrief(o.id, o.fullName, o.email) " +
>        "FROM Order o JOIN o.users u WHERE o.city = :city")
> List<UserBrief> findUserBriefsByOrderCity(@Param("city") String city);
> ```
> 
> ### 3.4. Маленький `LIMIT` без индекса на `ORDER BY`
> 
> ```sql
> -- 1M строк, сортировка по created_at DESC, берём 10
> SELECT * FROM users ORDER BY created_at DESC LIMIT 10;
> ```
> 
> Без индекса: БД **сортирует все 1 000 000 строк**, потом берёт 10.
> С индексом `ON users (created_at DESC)`: БД просто читает первые 10 записей из индекса. **10 операций вместо 1 000 000.**
> 
> ```sql
> CREATE INDEX idx_users_created_desc ON users (created_at DESC);
> ```
> 
> ### 3.5. Статистика устарела
> 
> Если ты вставил 500 000 новых строк за ночь, а `ANALYZE` последний раз был месяц назад — планировщик «думает», что в таблице 500K строк, и выбирает **неоптимальный план**.
> 
> ```sql
> -- Ручное обновление статистики
> ANALYZE users;
> 
> -- Или настрой autovacuum (PostgreSQL):
> ALTER SYSTEM SET autovacuum_analyze_scale_factor = 0.05; -- анализ после 5% изменений
> ```

> ## Шаг 5. Чек-лист: что делать, когда запрос «тормозит»
> 
> Выполняй **по порядку**, останавливайся, как только стало быстро:
> 
> | # | Действие | Инструмент |
> |---|---|---|
> | 1 | `EXPLAIN ANALYZE` — увидь план | psql, DBeaver |
> | 2 | Есть `Seq Scan` на большой таблице? | В выводе EXPLAIN |
> | 3 | Создай индекс по столбцам из `WHERE` (порядок: `=` → `LIKE 'x%'` → диапазон) | `CREATE INDEX` |
> | 4 | `ANALYZE table;` — обнови статистику | psql |
> | 5 | `EXPLAIN ANALYZE` ещё раз — убедись, что `Index Scan` | psql |
> | 6 | Убери `SELECT *` → перечисли столбцы | SQL |
> | 7 | Проверь N+1 в Hibernate (включи `spring.jpa.show-sql` + `spring.jpa.properties.hibernate.format_sql=true`) | Логи приложения |
> | 8 | Если сортировка — есть ли индекс на `ORDER BY`? | EXPLAIN |
> | 9 | Если всё равно медленно — смотри `work_mem`, `shared_buffers` (настройки БД) | `SHOW work_mem;` |
> | 10 | Если запрос вызывается часто — кэшируй результат (Redis, Caffeine) | Java-код |
>

> 
> ## Шаг 6. Что НЕ делать (частые ошибки джуниора)
> 
> - ❌ **Создавать 10 индексов на таблицу «на всякий случай».** Каждый индекс замедляет INSERT/UPDATE/DELETE.
> - ❌ **Добавлять `CROSS JOIN` или подзапрос** вместо простого `JOIN` + `WHERE`.
> - ❌ **Игнорировать `LIMIT`.** Без `LIMIT` на 1M строк даже быстрый индекс вернёт 100 000 строк в память.
> - ❌ **Запускать `SELECT *`** в продакшен-логировании. Ты читаешь все BLOB-поля.
>

> ## Итого (TL;DR)
>

> Привет, Игорь! Задача классическая, на собеседованиях её спрашивают как «разминку». Разберём **два подхода** — от простого к более правильному, чтобы ты понял не только «как пишется», но и **почему**.
> 
> ---
> 
> ## Шаг 1. Что такое палиндром
> 
> **Палиндром** — это строка (или число), которая читается **одинаково** слева направо и справа налево.
> 
> Примеры:
> - `«топот»` — да
> - `«мадам»` — да
> - `«привет»` — нет
> - `«A man a plan a canal Panama»` — да, если игнорировать пробелы и регистр
> 
> В этой задаче сделаем **два уровня**:
> 1. **Базовый** — строка палиндром, если она совпадает со своим обратным вариантом (регистр и пробелы учитываются).
> 2. **Улучшенный** — игнорируем пробелы, знаки препинания и регистр (как в реальном собеседовании).
> 
> ---
> 
> ## Шаг 2. Подход №1: «Обрати строку и сравни» (простой)
> 
> Идея: разворачиваем строку задом наперёд и сравниваем с оригиналом.
> 
> ```java
> package com.example.palindrome;
> 
> /**
>  * Подход 1: реверс + сравнение.
>  *
>  * Сложность:
>  *   Время  — O(n), где n — длина строки (один проход на реверс + одно на сравнение)
>  *   Память — O(n), т.к. строим новую строку (reverse())
>  */
> public class PalindromeSimple {
> 
>     /**
>      * Проверяет, является ли строка палиндромом.
>      * Учитывает регистр и спецсимволы: "Ab" != "ba".
>      *
>      * @param s проверяемая строка
>      * @return true, если pалиндром
>      */
>     public static boolean isPalindrome(String s) {
>         // 1. Защита от null (чтобы не получить NullPointerException)
>         if (s == null) {
>             return false;
>         }
> 
>         // 2. Строки длины 0 и 1 — тривиально палиндром
>         if (s.length() <= 1) {
>             return true;
>         }
> 
>         // 3. Разворачиваем строку: "тест" → "тсет"
>         //    new StringBuilder(s).reverse() — стандартный способ разворота в Java
>         String reversed = new StringBuilder(s).reverse().toString();
> 
>         // 4. Сравниваем оригинал с развёрнутой
>         //    equals() сравнивает по содержанию, а не по ссылке
>         return s.equals(reversed);
>     }
> 
>     // ---------- Тест ----------
>     public static void main(String[] args) {
>         // Тестовые случаи: строка → ожидаемый результат
>         System.out.println(isPalindrome("топот"));      // true
>         System.out.println(isPalindrome("мадам"));      // true

> ```

>  */

> 
>     /**
>      * Проверяет, является ли строка палиндромом.
>      * Регистр и пробелы УЧИТЫВАЮТСЯ (строгая проверка).
>      *
>      * @param s проверяемая строка
>      * @return true, если палиндром
>      */
>     public static boolean isPalindromeStrict(String s) {
>         // Защита от null
>         if (s == null) {
>             return false;
>         }
> 
>         // Левый указатель — стартуем с первого символа (индекс 0)
>         int left = 0;
> 
>         // Правый указатель — стартуем с последнего символа (индекс length-1)
>         int right = s.length() - 1;
> 
>         // Пока указатели НЕ пересеклись:
>         //   left < right → ещё есть пара символов для сравнения
>         //   left == right → середна строки (для нечётной длины) — всё, стоп

>             right--;  // двигаем влево
>         }
> 
>         // Дойдя сюда, все пары совпали → это палиндром
>         return true;
>     }
